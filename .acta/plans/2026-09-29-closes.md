# Closes Field Implementation Plan

> **For agentic workers:** run this plan with acta:build, task by task. Steps use checkbox (`- [ ]`) syntax, and acta reads those boxes as task progress.

**Goal:** One piece of work can close several items: a `closes:` list in spec, plan and bug frontmatter, a plan's `**Spec:**` line that always links, and a spec status that is always derived once the spec has a plan.

**Architecture:** The board gains one linking pass (`linkCloses`) after every item is known, two item fields (`Closes`, `ClosedBy`), and two small changes in `linkPlan` and `derive`. The CLI and TUI print the new fields. Skill text tells agents to write `closes:`. Existing `.acta` files are migrated on the same branch.

**Tech Stack:** Go (stdlib), `internal/board`, `internal/cli`, `internal/tui`, Markdown skills, `internal/plugincheck`.

**Spec:** `.acta/specs/2026-09-29-closes-design.md`

## Global Constraints

- Implement ponytail-lazy: YAGNI, then existing code, then stdlib, then native, then an installed dependency, then one line, then the minimum; never cut validation, security or accessibility.
- `parent:` stays one value and sets the tree place only.
- `closes:` is read on specs, plans and bugs only; on any other kind it is ignored.
- Targets may be a scratch item, a spec or a debt item. Anything else is a problem on the item that wrote `closes:`, never a load failure: one bad entry must not hide the rest of the board.
- Problem texts, verbatim: `closes <entry> not found`, `closes <entry>: a <kind> cannot be closed`, `written status <X> ignored, derived <Y>`.
- Debt items are never derived from `closes:`; only `acta:land` ticks them.
- Comments in plain English a 10-year-old can read; say why, not what.
- Gates: `gofmt -l .` prints nothing, `go vet ./...` is ok, `go test ./...` is green.

# TUI scroll at 60fps

## Words

### 2026-09-30

User ask 2026-09-30: "kita bisa bikin scroll performance jauh lebih cepet gak? make it 60fps".

Debug phase 1 findings (real board, 200x55, idle, main 0cfe59a):
- The wheel path is serial. The first notch arms a 16 ms tick (internal/tui/model.go:562), the tick applies the delta (model.go:232), View runs, then the Bubble Tea v1 renderer flushes on its own 60fps ticker. One screen step costs about 16 + 7.5 + up to 16.6 ms, so the best case is near 30 fps.
- View of the detail pane takes 7.5 ms, the list pane 2.7 ms. Most of it is ansi.StringWidth through lipgloss.JoinHorizontal, Width, fit and pad.
- geometry, rowsOf, doneRows and ordered sort every item (idNum calls strconv.Atoi) many times per notch, tick and draw.
- Related debt: DBT-0030.07 (detailParts builds the whole detail 3 to 4 times per frame).

### 2026-09-30

Approach: user picked option 1. Trace + timing fix (apply the first notch at once, gather the rest, tea.WithFPS(120)) + build sorted rows once per board/tab/order change + build detailParts once per frame (closes DBT-0030.07). Per-pane render cache is a later plan only if the trace still fails.

### 2026-09-30

Design section 1 approved: metric corrected (per-notch p95 <= 16.7 ms is not reachable at ~220 notches/s). Pass = flush gap p95 <= 16.7 ms and fps >= 55 between first and last notch, plus first-notch-after-a-pause to flush p95 <= 16.7 ms. Trace: internal/tui/trace.go, mutex tracer, nil = no work; cli.go opens ACTA_TUI_TRACE and wraps stdout with tea.WithOutput so each Write is a flush; open failure warns on stderr and runs untraced; lines notch/view/flush; summary line on quit; tests use fake clocks, no sleeps.

### 2026-09-30

Design section 2 approved: first notch with no tick armed scrolls at once and arms a 16 ms tick; notches while armed gather; tick with delta scrolls and re-arms; empty tick disarms; mark and cross-pane flush rules unchanged; tea.WithFPS(120) in cli.go. Old wheel tests that assume the first notch waits are rewritten, not deleted.

### 2026-09-30

Design section 3 approved: detailParts is already cached (DBT-0030.07 likely stale) and row sorting is 2.5% of View, so both are dropped. Instead, draw joins the wide layout by plain per-line concat (paneView lines are already padded to box width), keeping fit only for the narrow layout and tab rows. wheelFrame goes 16 -> 12 ms so applies never skip two 8.3 ms flush ticks. Tests: existing view output unchanged, every frame line exactly m.width wide (wide, narrow, unicode, cut lines), bench fixed to scroll one way on a long board.
